LLM APIs and tool calling, from scratch

No framework. Just messages, JSON schemas and a loop, which is what LangChain, LlamaIndex, the OpenAI Agents SDK and your Bedrock bot all do under the hood.

You've already shipped an agent with 14 tools. This note gives you the vocabulary and a clean, provider-agnostic version you can write on a whiteboard, or rebuild in public in under 150 lines.

1. The mental model: a stateless function over a list of messages

A chat model API is a pure function: messages in, one message out. It remembers nothing between calls. Every turn, you resend the whole conversation: system prompt, user turns, assistant turns, and tool results.

Role Who writes it Purpose
system (or developer) You Rules, persona, output format, tool policy
user The end user The question or task
assistant The model Text, or tool calls (a request for you to run something)
tool You The result of running a tool, linked by tool_call_id

Knobs worth knowing: model, temperature (randomness; use 0 or close to it for extraction and tools), max_tokens / max_completion_tokens (an output cap), tools, tool_choice (auto, none, required, or a specific function), response_format (JSON / JSON schema), and stream.

2. One client, many providers

The OpenAI Chat Completions format is the de facto lingua franca. Many providers and local servers expose an OpenAI-compatible endpoint, including Google Gemini, Groq, OpenRouter, Together, and local servers like Ollama and vLLM. That lets one client and a base_url cover most of them. Anthropic's Messages API and AWS Bedrock's Converse API (what your work bot uses) have their own shapes, but the same concepts: content blocks, tool_use / tool_result, and a stop reason.

import os
from openai import AsyncOpenAI

# Point at any OpenAI-compatible server via env vars, e.g.
#   Ollama:  LLM_BASE_URL=http://localhost:11434/v1  LLM_MODEL=llama3.1  (any key works)
#   OpenAI:  leave LLM_BASE_URL unset, set LLM_API_KEY, pick a model
client = AsyncOpenAI(base_url=os.getenv("LLM_BASE_URL"), api_key=os.getenv("LLM_API_KEY", "not-needed"))
MODEL = os.getenv("LLM_MODEL", "llama3.1")

async def ask(question: str) -> str:
    resp = await client.chat.completions.create(
        model=MODEL, temperature=0,
        messages=[{"role": "system", "content": "Answer in one sentence."},
                  {"role": "user", "content": question}])
    print(resp.usage)                       # prompt/completion token counts, when the server reports them
    return resp.choices[0].message.content or ""

Check each provider's docs for which features (tools, JSON schema, streaming usage) their compatible endpoint actually supports. Coverage varies.

3. Tools are JSON schemas plus your code

The model never runs anything. You describe each tool with a name, a description and a JSON Schema for its arguments. The model may answer with a structured request like "call top_stores with {"metric": "orders", "k": 3}". Your code validates the request, runs it, and sends the result back.

Pydantic writes the schema for you, so the args model doubles as your DTO and your validator:

import asyncio, json, typing
from collections.abc import Awaitable, Callable
from typing import Literal
from pydantic import BaseModel, Field, ValidationError

STORES = {  # toy data so the example runs anywhere
    "S01": {"city": "Delhi", "orders": 1200, "rating": 4.1},
    "S02": {"city": "Noida", "orders": 950, "rating": 4.5},
    "S03": {"city": "Gurugram", "orders": 1430, "rating": 3.9},
}

ToolFn = Callable[[typing.Any], Awaitable[str]]
REGISTRY: dict[str, tuple[type[BaseModel], ToolFn, str]] = {}

def tool(description: str):
    """Register an async function whose single parameter `args` is a pydantic model."""
    def deco(fn: ToolFn) -> ToolFn:
        args_model = typing.get_type_hints(fn)["args"]
        REGISTRY[fn.__name__] = (args_model, fn, description)
        return fn
    return deco

class TopStoresArgs(BaseModel):
    metric: Literal["orders", "rating"]
    k: int = Field(default=3, ge=1, le=10)

@tool("Return the top-k stores ranked by a metric.")
async def top_stores(args: TopStoresArgs) -> str:
    ranked = sorted(STORES.items(), key=lambda kv: kv[1][args.metric], reverse=True)
    return json.dumps([{"id": sid, **row} for sid, row in ranked[: args.k]])

class StoreArgs(BaseModel):
    store_id: str = Field(pattern=r"^S\d{2}$", description="Store id like S01")

@tool("Return all KPIs for one store.")
async def store_kpis(args: StoreArgs) -> str:
    if args.store_id not in STORES:
        raise KeyError(f"no store {args.store_id}")
    return json.dumps(STORES[args.store_id])

def tool_specs() -> list[dict]:
    return [{"type": "function",
             "function": {"name": name, "description": desc, "parameters": model.model_json_schema()}}
            for name, (model, _, desc) in REGISTRY.items()]

Good tool design matters more than prompt tricks: - Few, well-named, typed tools with clear descriptions. The descriptions are prompts. - Narrow parameters (Literal, ranges, patterns) instead of "free SQL", which is the same thing your typed DuckDB tools do. - Small, structured results. Return the 10 rows the model needs, not 10,000. Every result costs tokens on every later turn. - Errors as data. Return {"error": ...} so the model can fix its call instead of crashing the loop.

4. The agent loop

SYSTEM = ("You answer questions about stores using the tools. "
          "Never invent numbers; if a tool errors, fix the call or say you can't.")

async def dispatch(name: str, raw_args: str) -> str:
    if name not in REGISTRY:
        return json.dumps({"error": f"unknown tool {name}"})
    model, fn, _ = REGISTRY[name]
    try:
        args = model.model_validate_json(raw_args or "{}")
    except ValidationError as e:
        return json.dumps({"error": "invalid arguments", "details": str(e)})
    try:
        async with asyncio.timeout(10):
            return await fn(args)
    except Exception as e:                       # tool failures go back to the model as data
        return json.dumps({"error": type(e).__name__, "message": str(e)})

async def run_agent(question: str, max_turns: int = 6) -> str:
    messages: list[dict] = [{"role": "system", "content": SYSTEM},
                            {"role": "user", "content": question}]
    for _ in range(max_turns):
        resp = await client.chat.completions.create(
            model=MODEL, messages=messages, tools=tool_specs(), temperature=0)
        msg = resp.choices[0].message
        if not msg.tool_calls:
            return msg.content or ""
        messages.append(msg.model_dump(exclude_none=True))      # keep the assistant's tool request
        results = await asyncio.gather(*(dispatch(tc.function.name, tc.function.arguments)
                                         for tc in msg.tool_calls))
        for tc, result in zip(msg.tool_calls, results):
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
    return "Stopped after too many steps."                      # guard against loops

# asyncio.run(run_agent("Which Noida or Delhi store has the better rating?"))

Three details interviewers probe: 1. The assistant message with tool_calls must be appended before the tool results, and every tool_call_id needs a matching tool message. Otherwise the API rejects the next request. 2. Models can request several tools in one turn (parallel tool calls). Run them concurrently, because they're independent by construction. 3. max_turns (and ideally a token or cost budget) is your circuit breaker against loops.

5. Structured outputs: when you want data, not a chat

For extraction and classification, like your Gemini review tagging, skip tools and ask for JSON that matches a schema. Providers that support structured outputs constrain decoding to your schema, so the output parses. OpenAI's strict mode, for example, requires every field to be required and additionalProperties: false, which extra="forbid" produces.

from pydantic import ConfigDict

class Triage(BaseModel):
    model_config = ConfigDict(extra="forbid")          # -> additionalProperties: false
    category: Literal["delivery", "quality", "billing", "other"]
    urgent: bool
    summary: str = Field(description="One sentence, no PII")

async def triage(review: str) -> Triage:
    resp = await client.chat.completions.create(
        model=MODEL, temperature=0,
        messages=[{"role": "system", "content": "Classify the customer review."},
                  {"role": "user", "content": review}],
        response_format={"type": "json_schema",
                         "json_schema": {"name": "triage", "strict": True,
                                         "schema": Triage.model_json_schema()}})
    return Triage.model_validate_json(resp.choices[0].message.content or "")

The OpenAI SDK also has a parse helper that accepts the pydantic class directly, and libraries like Instructor add validate-and-retry on top of many providers. If a server only supports {"type": "json_object"}, put the schema in the prompt and keep the pydantic validation and repair loop from note 02.

6. Guardrails: defence in depth

  • Least privilege beats prompting. Give the tool a read-only DB user and parameterised queries. "Please don't drop tables" in the system prompt is not a control.
  • Prompt injection is real. Text inside tool results or retrieved documents can contain instructions. Treat it as data, and never let it trigger side-effecting tools without a check or a human confirmation.
  • Side effects need confirmation (sending, paying, deleting). Use a human-in-the-loop step, or at least idempotency keys.
  • Budgets: max turns, max tokens per request, per-user rate limits and timeouts.
  • Routing: a cheap classifier or rule step can decide whether a question is in scope before the expensive loop runs. Your semantic routing guards are this pattern.

Libraries exist for parts of this (e.g. Guardrails AI, NVIDIA NeMo Guardrails, provider moderation endpoints), but the core is plain code you control.

7. Tokens, context windows, cost and latency

  • A token is a sub-word chunk. Each model family has its own tokenizer, so counts differ between providers. tiktoken counts tokens for OpenAI models. For everything else, read usage from the response.
  • The context window holds input plus output. Long tool results and chat history eat it fast. Common strategies: keep the last N turns, summarise older ones, and trim tool outputs to what's needed.
  • Cost is roughly input_tokens × input price + output_tokens × output price. Output tokens usually cost more per token. Because the whole history is resent every turn, a 6-step agent loop pays for the early messages 6 times.
  • Latency is dominated by output length and the number of sequential model calls. You can cut it with fewer loop steps, parallel tool calls, a smaller or faster model for easy steps, streaming (for perceived latency), and prompt caching. Several providers discount or speed up a repeated prompt prefix. To benefit, put the stable parts (system prompt, tool specs) first.
import tiktoken                                        # OpenAI tokenizers only
enc = tiktoken.get_encoding("o200k_base")              # used by recent OpenAI models
print(len(enc.encode("Which Noida store has the best rating?")))

Common interview questions

  • Walk me through what happens when an LLM calls a tool. The model can't execute anything. It emits a structured request, your code validates and runs it, the result goes back as a tool message, and the loop continues until the model replies with plain text or you hit a budget.
  • How do you stop an agent from looping or running up cost? Max turns, token and cost budgets, timeouts, deduplicating repeated identical calls, and a planner or router step for simple questions.
  • How do you make tool use safe? Least-privilege credentials, typed and validated arguments, allow-lists, row and size limits, human confirmation for side effects, and treating tool output as untrusted (prompt injection).
  • Tool calling vs structured outputs? Tools when the model has to choose actions or fetch data. Structured outputs when you want one typed answer from one call.
  • Your agent is slow. What do you do? Measure first with traces. Then cut sequential steps, parallelise tools, shrink prompts and tool outputs, use prompt caching, route easy queries to a smaller model, and stream the answer.

An agent is just a while-loop with a model inside. Like any other system, what makes it work in production is the engineering around it: types, timeouts, budgets and permissions.
