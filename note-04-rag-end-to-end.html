RAG end to end: chunk, embed, retrieve, rerank, cite

Retrieval-augmented generation is search plus a prompt. Most RAG quality problems are search problems, and that's good news for someone who thinks in indexes and SQL.

RAG answers questions from your documents: policies, menus, runbooks, review dumps. At query time you fetch the most relevant passages and put them in the prompt with an instruction to answer only from them, with citations. It doesn't retrain the model. It gives the model an open book.

1. Parsing and chunking

Garbage in, garbage retrieved. Before you tune anything, look at the extracted text: PDF tables, headers and footers repeated on every page, and broken hyphenation all hurt retrieval.

Why chunk at all? Embeddings of short, focused passages match questions better than one vector for a 40-page document, and you can only fit so much into the prompt.

Strategy How Good for
Fixed size + overlap N tokens/chars with ~10-20% overlap Quick baseline
Recursive / structural Split on headings → paragraphs → sentences until under the size Most docs (a common default)
Semantic Split where adjacent-sentence embeddings diverge Long unstructured text
Document-aware One FAQ entry, one ticket, one table row group per chunk Structured sources

Keep metadata with every chunk (doc id, title, section, URL, date, access level). You'll need it for filtering, citations and permissions. A cheap, effective trick is to prepend the document title and section heading to the chunk text before embedding, so "Refunds take 5-7 days" still knows it belongs to the "Wallet cashback policy" document.

import re
from pydantic import BaseModel

class Chunk(BaseModel):
    id: str
    doc_id: str
    title: str
    text: str

def chunk_doc(doc_id: str, title: str, text: str, max_chars: int = 800, overlap: int = 150) -> list[Chunk]:
    """Paragraph-first chunking with character overlap. Swap chars for tokens in production."""
    paras = [p.strip() for p in re.split(r"\n\s*\n", text) if p.strip()]
    chunks: list[str] = []
    buf = ""
    for p in paras:
        if len(buf) + len(p) + 1 <= max_chars:
            buf = f"{buf}\n{p}".strip()
            continue
        if buf:
            chunks.append(buf)
        while len(p) > max_chars:                     # very long paragraph: hard split
            chunks.append(p[:max_chars])
            p = p[max_chars - overlap:]
        buf = (chunks[-1][-overlap:] + "\n" + p) if chunks else p
    if buf:
        chunks.append(buf)
    return [Chunk(id=f"{doc_id}#{i}", doc_id=doc_id, title=title,
                  text=f"{title}\n{c}") for i, c in enumerate(chunks)]

2. Embeddings and vector search

An embedding model maps text to a vector so that similar meanings land close together. You embed every chunk once, embed each query at request time, and return the nearest chunks by cosine similarity. With unit-normalised vectors, cosine similarity is just a dot product.

Embedding options: hosted APIs (OpenAI, Gemini, Cohere, Voyage and others), or open models via sentence-transformers or Ollama (e.g. the BGE, E5, GTE and nomic families). Check the MTEB leaderboard as a starting point, then evaluate on your own data, because leaderboard rank doesn't always carry over to a specific domain. Always embed queries and documents with the same model. Some models expect different prefixes for queries and passages, so read the model card.

import os
import numpy as np
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url=os.getenv("LLM_BASE_URL"), api_key=os.getenv("LLM_API_KEY", "not-needed"))
EMBED_MODEL = os.getenv("EMBED_MODEL", "nomic-embed-text")     # e.g. via Ollama

async def embed(texts: list[str]) -> np.ndarray:
    resp = await client.embeddings.create(model=EMBED_MODEL, input=texts)
    vecs = np.array([d.embedding for d in resp.data], dtype=np.float32)
    return vecs / np.linalg.norm(vecs, axis=1, keepdims=True)   # unit length -> dot = cosine

def dense_search(q: np.ndarray, matrix: np.ndarray, k: int) -> list[int]:
    scores = matrix @ q                                         # brute force: fine up to ~1e5 chunks
    return list(np.argsort(-scores)[:k])

At scale you use an approximate nearest neighbour (ANN) index, typically HNSW or IVF, which trades a little recall for big speedups. Where it lives is mostly an ops decision: pgvector (if you already run Postgres), FAISS (a library), Chroma or LanceDB (embedded), Qdrant, Weaviate or Milvus (servers), OpenSearch/Elasticsearch, or DuckDB's vss extension for a small analytics-style setup.

3. Hybrid search: BM25 plus vectors

Dense retrieval is good at paraphrase ("my money didn't come back" ↔ "refund delay") and bad at exact tokens: order ids, SKU codes, error codes, rare names. BM25, the classic keyword ranking behind Lucene and Elasticsearch, is the opposite. Running both and fusing the results is a robust default.

Reciprocal Rank Fusion (RRF) merges ranked lists using only the ranks: score(d) = Σ 1 / (k + rank_i(d)), with k = 60 as the constant from the original paper. You don't need to calibrate BM25 scores against cosine scores.

from rank_bm25 import BM25Okapi

def tokenize(s: str) -> list[str]:
    return re.findall(r"[a-z0-9]+", s.lower())

class HybridIndex:
    def __init__(self, chunks: list[Chunk], matrix: np.ndarray | None = None) -> None:
        self.chunks, self.matrix = chunks, matrix
        self.bm25 = BM25Okapi([tokenize(c.text) for c in chunks])

    def bm25_search(self, query: str, k: int) -> list[int]:
        scores = self.bm25.get_scores(tokenize(query))
        return list(np.argsort(-scores)[:k])

    def search(self, query: str, q_vec: np.ndarray | None = None, k: int = 5, pool: int = 30) -> list[Chunk]:
        ranked_lists = [self.bm25_search(query, pool)]
        if q_vec is not None and self.matrix is not None:
            ranked_lists.append(dense_search(q_vec, self.matrix, pool))
        return [self.chunks[i] for i in rrf(ranked_lists)[:k]]

def rrf(ranked_lists: list[list[int]], k: int = 60) -> list[int]:
    scores: dict[int, float] = {}
    for ranking in ranked_lists:
        for rank, idx in enumerate(ranking, start=1):
            scores[idx] = scores.get(idx, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.__getitem__, reverse=True)

4. Reranking

First-stage retrieval is built for recall: it's cheap, it scans everything, and it returns 20-50 candidates. A reranker is built for precision. A cross-encoder reads the query and each candidate together and scores how relevant the candidate is. That's more accurate than comparing two separately computed vectors, but too slow to run over the whole corpus, so it only re-orders the shortlist.

from sentence_transformers import CrossEncoder      # uv add sentence-transformers

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank(query: str, candidates: list[Chunk], top_n: int = 5) -> list[Chunk]:
    scores = reranker.predict([(query, c.text) for c in candidates])
    order = np.argsort(-np.asarray(scores))[:top_n]
    return [candidates[i] for i in order]

Alternatives include hosted rerank APIs (e.g. Cohere, Voyage, Jina), BGE rerankers, or an LLM as a listwise reranker (more expensive). Add a reranker once you have an eval set that shows the first stage finds the right chunk but ranks it too low.

5. Generation with citations

Number the chunks, tell the model to use only them, and require citations. Then verify in code that every cited id exists and every factual sentence has one. This is grounding as a contract, the same way you validate tool args.

from pydantic import Field

class Answer(BaseModel):
    answer: str
    citations: list[str] = Field(description="Chunk ids like 'policy#3' that support the answer")
    answerable: bool

PROMPT = """Answer the question using ONLY the sources below.
If the sources don't contain the answer, set answerable=false and say you don't know.
Cite the source ids you used.

{sources}

Question: {question}"""

def build_prompt(question: str, chunks: list[Chunk]) -> str:
    sources = "\n\n".join(f"[{c.id}] {c.text}" for c in chunks)
    return PROMPT.format(sources=sources, question=question)

def check_citations(ans: Answer, chunks: list[Chunk]) -> list[str]:
    allowed = {c.id for c in chunks}
    problems = [f"unknown citation {cid}" for cid in ans.citations if cid not in allowed]
    if ans.answerable and not ans.citations:
        problems.append("answer has no citations")
    return problems

Use the structured-outputs call from note 03 with Answer as the schema, and show the citations in the UI as links back to the source document.

6. Common failure modes and fixes

Symptom Likely cause Fix
Misses exact ids / codes Dense-only retrieval Add BM25 (hybrid) or metadata filters
Right doc, wrong part Chunks too big or too small Tune size and overlap, use structural chunking, add headings to chunks
Answer ignores a retrieved fact Too many chunks, relevant one buried Rerank, send fewer chunks; long-context models are known to use mid-context information less reliably ("Lost in the Middle", Liu et al.)
Confident wrong answers No "I don't know" path answerable flag, a relevance threshold, citation checks
Stale answers Index not refreshed Scheduled re-indexing keyed on doc hash/updated_at (like your cron pipelines)
Multi-part questions fail One query can't fetch everything Query decomposition or rewriting, or an agent that calls retrieval as a tool
Users see docs they shouldn't No access control in retrieval Filter by permissions in the retriever, not in the prompt

Know the vocabulary for agentic RAG too: retrieval exposed as a tool, so the model can search several times and refine its query. It's often better for complex questions, and it costs more turns.

Common interview questions

  • RAG vs fine-tuning? RAG for knowledge that changes or needs citations and access control. Fine-tuning for behaviour, format or style, or a narrow task at lower cost. They're often combined.
  • How do you choose chunk size? Start with a structural or recursive baseline, then pick by measured retrieval recall on a labelled question set, not by intuition.
  • Why hybrid search? Dense handles paraphrase, BM25 handles exact tokens, and RRF fuses them without score calibration.
  • What does a reranker add, and what does it cost? Higher precision in the top few results, for added latency per query. Use it on a candidate pool of tens, never the whole corpus.
  • How do you reduce hallucinations? Better retrieval first, then grounding instructions, structured output with an "unanswerable" path, citation verification, and evals for faithfulness.
  • How would you debug a bad answer? Split it into retrieval, then context, then generation (the diagram above), using traces of what was retrieved.
