The real split in ML work

An ML engineering job is roughly two parts. One is modelling: picking models, features, prompts, metrics. The other is engineering: turning that into a service that is tested, versioned, rate-limited, observable, and doesn't fall over at 2am. Data scientists often struggle with the second part. You spent four years training for it.

The frustration you feel at work (no version control, reports breaking at the last minute) isn't a sign you're bad at this. It's a sign the environment lacks engineering. The ML engineer roles you're aiming for are the engineering.

1. Interfaces → estimator API and Protocols

Java made you think in contracts. Python is duck-typed, but serious ML code adds the contract back with Protocol. scikit-learn's whole ecosystem works because every model honours the same fit/predict interface, which is the same idea as programming to an interface.

Java

public interface Classifier {
    void fit(double[][] X, int[] y);
    int[] predict(double[][] X);
}

public class MajorityClassifier implements Classifier {
    private int label;
    public void fit(double[][] X, int[] y) {
        label = mode(y);
    }
    public int[] predict(double[][] X) {
        int[] out = new int[X.length];
        Arrays.fill(out, label);
        return out;
    }
}

Python

from typing import Protocol
import numpy as np
from sklearn.base import BaseEstimator, ClassifierMixin

class Classifier(Protocol):
    def fit(self, X, y) -> "Classifier": ...
    def predict(self, X) -> np.ndarray: ...

class MajorityClassifier(BaseEstimator, ClassifierMixin):
    def fit(self, X, y):
        vals, counts = np.unique(y, return_counts=True)
        self.label_ = vals[counts.argmax()]
        return self                 # sklearn convention
    def predict(self, X):
        return np.full(len(X), self.label_)

Same move for LLMs: define an LLMClient Protocol with complete(messages, tools), then Gemini/Claude/OpenAI become interchangeable implementations. That's the provider abstraction you'd want if a manager suddenly says "switch models".

2. Concurrency → async LLM calls and batching

LLM calls are slow, I/O-bound network calls with rate limits. That's the textbook case for bounded concurrency, which you learned with thread pools.

Java

ExecutorService pool = Executors.newFixedThreadPool(8);
List<CompletableFuture<String>> fs = reviews.stream()
    .map(r -> CompletableFuture.supplyAsync(
        () -> llm.classify(r), pool))
    .toList();
List<String> labels = fs.stream()
    .map(CompletableFuture::join).toList();

Python

import asyncio

sem = asyncio.Semaphore(8)          # = fixed pool size

async def classify(r: str) -> str:
    async with sem:
        return await llm.aclassify(r)

async def run(reviews: list[str]) -> list[str]:
    return await asyncio.gather(*(classify(r) for r in reviews))

Add batching (several reviews per prompt) and retries with exponential backoff and you have the skeleton of a production LLM pipeline.

4. LLD and patterns → the agent tool registry

An agent is a loop: the model picks a tool, you validate the args, run it, and feed the result back. Choosing a tool by name is the Strategy + Registry pattern, and guardrails are a Chain of Responsibility. Your Bedrock bot with 14 typed tools and routing guards was an LLD exercise.

Java

interface Tool { String name(); Object run(Map<String,Object> args); }

class ToolRegistry {
  private final Map<String, Tool> tools = new HashMap<>();
  void register(Tool t) { tools.put(t.name(), t); }
  Object dispatch(String name, Map<String,Object> args) {
    Tool t = tools.get(name);
    if (t == null) throw new IllegalArgumentException(name);
    return t.run(args);
  }
}

Python

from typing import Callable
from pydantic import BaseModel

REGISTRY: dict[str, tuple[type[BaseModel], Callable]] = {}

def tool(args: type[BaseModel]):
    def deco(fn):
        REGISTRY[fn.__name__] = (args, fn)
        return fn
    return deco

def dispatch(name: str, raw: dict):
    if name not in REGISTRY:
        raise ValueError(f"unknown tool {name}")
    model, fn = REGISTRY[name]
    return fn(model(**raw))   # validated args

5. JUnit → pytest and eval harnesses

Unit tests check deterministic code. LLM output isn't deterministic, so ML teams add evals: a fixed golden set, a scoring function, and a pass-rate threshold that runs in CI. Think of it as JUnit with a score instead of a strict assert, or as an A/B readout for prompts, which you already do professionally.

Java

@Test
void rejectsNonSelect() {
  assertThrows(IllegalArgumentException.class,
      () -> guard.check("DROP TABLE users"));
}

Python

import pytest, json

def test_rejects_non_select():
    with pytest.raises(ValueError):
        guard.check("DROP TABLE users")

def test_eval_pass_rate():
    cases = [json.loads(l) for l in open("evals/golden.jsonl")]
    passed = sum(agent.answer(c["q"]) == c["expected"] for c in cases)
    assert passed / len(cases) >= 0.8    # regression gate

6. WorkQueue → LLM rate limiting and job queues

LLM providers limit requests and tokens per minute. Your Lua token bucket in Redis is exactly the right tool for keeping many workers under a shared limit. In ML system design rounds, "process 1M documents with an LLM" is basically WorkQueue: a producer, a queue, workers, a rate limiter, retries, and a results store.

import asyncio, time

class TokenBucket:                       # in-process version of your Redis+Lua limiter
    def __init__(self, rate_per_s: float, capacity: int):
        self.rate, self.cap = rate_per_s, capacity
        self.tokens, self.t = capacity, time.monotonic()
        self.lock = asyncio.Lock()

    async def acquire(self, n: int = 1):
        while True:
            async with self.lock:
                now = time.monotonic()
                self.tokens = min(self.cap, self.tokens + (now - self.t) * self.rate)
                self.t = now
                if self.tokens >= n:
                    self.tokens -= n
                    return
            await asyncio.sleep(n / self.rate)

Across several machines you'd move it back into Redis, just as you did. That's a strong talking point: "I've implemented a distributed token bucket, here's how I'd apply it to LLM TPM limits."
