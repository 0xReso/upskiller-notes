Python for AI engineers: the bits that matter

You don't need all of Python. You need the slice that turns "a notebook that calls an LLM" into a service you'd trust in production.

You already write Python every day, so this isn't a syntax tour. It's the specific toolkit AI engineering teams use: typed data at the edges, concurrency for slow network calls, retries for flaky APIs, streaming, clean resource handling, reproducible packaging, and tests. Each section ends with what you'd actually say in an interview.

1. Type hints: contracts for a dynamic language

Python ignores type hints at runtime. Tools like mypy and pyright, plus your editor, read them, and so do libraries like pydantic and FastAPI. For LLM code that's a big deal: the function signature becomes the documentation, and pydantic can turn it into a JSON schema.

from typing import Literal, Protocol, TypedDict

Sentiment = Literal["positive", "neutral", "negative"]   # a closed set, like a Java enum

class Message(TypedDict):          # typed shape for plain dicts (e.g. chat messages)
    role: Literal["system", "user", "assistant", "tool"]
    content: str

class LLM(Protocol):               # structural interface: anything with this method fits
    async def complete(self, messages: list[Message]) -> str: ...

def first_user_turn(messages: list[Message]) -> str | None:   # X | None replaces Optional[X]
    return next((m["content"] for m in messages if m["role"] == "user"), None)

Modern syntax to use: list[str] instead of List[str], X | None instead of Optional[X] (Python 3.10+), and Literal for fixed label sets.

2. Pydantic: where LLM text becomes data

An LLM returns a string. Your code wants an object it can trust. Pydantic v2 sits at that boundary: it gives you a JSON schema to send to the model, and it validates whatever comes back.

from typing import Literal
from pydantic import BaseModel, Field, ValidationError, field_validator

class ReviewLabel(BaseModel):
    sentiment: Literal["positive", "neutral", "negative"]
    topics: list[str] = Field(default_factory=list, max_length=5)
    confidence: float = Field(ge=0, le=1)

    @field_validator("topics")
    @classmethod
    def normalise(cls, v: list[str]) -> list[str]:
        return sorted({t.strip().lower() for t in v if t.strip()})

schema = ReviewLabel.model_json_schema()      # send this to the model as the output format

raw = '{"sentiment": "negative", "topics": ["Delivery ", "delivery", "cold food"], "confidence": 0.82}'
label = ReviewLabel.model_validate_json(raw)  # parse + validate in one step (fast, Rust core)
print(label.topics)                           # ['cold food', 'delivery']

try:
    ReviewLabel.model_validate_json('{"sentiment": "angry", "confidence": 2}')
except ValidationError as e:
    print(e.error_count(), "errors")          # 2 errors: bad literal, confidence > 1

The production pattern is validate, then repair. When validation fails, send the ValidationError text back to the model ("your output failed: …, fix it") and try once or twice more, then fail loudly. Most providers now also offer structured outputs (constrained decoding against your JSON schema), which makes malformed JSON rare. You should still validate, because a schema can't enforce business rules like "confidence must match the label".

dataclasses vs pydantic

@dataclass pydantic.BaseModel
Validation at runtime No (hints are just hints) Yes, with type coercion
JSON in/out Manual (asdict, json) model_validate_json, model_dump_json
JSON schema No model_json_schema()
Speed for plain objects Faster, stdlib only Slower than a dataclass, but fast for a validator
Use for Internal values you construct yourself Boundaries: LLM output, API requests, config, tool args

Rule of thumb: validate at the edges (pydantic), and use plain dataclasses inside. pydantic-settings reads config from env vars the same way.

3. async/await: the right tool for slow LLM calls

An LLM call spends most of its time waiting on the network. asyncio lets one thread juggle hundreds of those waits. It's the Python equivalent of your CompletableFuture pipelines, with an event loop instead of a thread pool.

import asyncio, random

async def classify(review: str) -> str:            # stand-in for a real LLM call
    await asyncio.sleep(random.uniform(0.2, 0.5))  # network wait; the loop runs others meanwhile
    return "negative" if "cold" in review else "positive"

async def classify_all(reviews: list[str], limit: int = 8) -> list[str]:
    sem = asyncio.Semaphore(limit)                 # bounded concurrency = respect rate limits

    async def one(r: str) -> str:
        async with sem:
            async with asyncio.timeout(30):        # per-call timeout (Python 3.11+)
                return await classify(r)

    return await asyncio.gather(*(one(r) for r in reviews))   # results keep input order

if __name__ == "__main__":
    reviews = ["pizza was cold", "great crust", "cold and late", "loved it"] * 5
    print(asyncio.run(classify_all(reviews))[:4])

Things worth knowing: - asyncio.gather(..., return_exceptions=True) collects failures instead of cancelling the batch. That's handy for bulk jobs where you log the failures and move on. - asyncio.TaskGroup (3.11+) is the structured alternative: if one task fails, its siblings are cancelled. - async only helps with I/O. CPU-heavy work like embedding locally or pandas transforms blocks the loop. Push it to asyncio.to_thread or a process pool. - The real clients are async-native: openai.AsyncOpenAI, anthropic.AsyncAnthropic, httpx.AsyncClient.

4. Retries with exponential backoff and jitter

LLM APIs fail in normal ways: 429 rate limits, 5xx errors, timeouts. Retry those. Don't retry 400 or 401 (your bug), and don't retry validation errors with the same prompt.

import asyncio, random
from collections.abc import Awaitable, Callable
from typing import TypeVar

T = TypeVar("T")

class Retryable(Exception): ...

async def with_backoff(fn: Callable[[], Awaitable[T]], attempts: int = 5,
                       base: float = 0.5, cap: float = 20.0) -> T:
    for n in range(attempts):
        try:
            return await fn()
        except Retryable:
            if n == attempts - 1:
                raise
            await asyncio.sleep(random.uniform(0, min(cap, base * 2 ** n)))  # "full jitter"
    raise AssertionError("unreachable")

In real code you'd usually reach for tenacity, and you'd set the SDK's own retry option too (the OpenAI and Anthropic Python SDKs both take a max_retries argument).

from openai import APIConnectionError, APITimeoutError, InternalServerError, RateLimitError
from tenacity import retry, retry_if_exception_type, stop_after_attempt, wait_random_exponential

@retry(retry=retry_if_exception_type((RateLimitError, APITimeoutError, APIConnectionError, InternalServerError)),
       wait=wait_random_exponential(min=1, max=30), stop=stop_after_attempt(5), reraise=True)
async def ask(client, model: str, prompt: str) -> str:
    resp = await client.chat.completions.create(model=model, messages=[{"role": "user", "content": prompt}])
    return resp.choices[0].message.content or ""

Jitter matters: without it, every worker that hit the 429 at the same moment retries at the same moment. That's the thundering-herd problem your WorkQueue token bucket was designed to stop.

5. Generators and streaming

A generator yields values lazily, so you can process a 10 GB file or a stream of tokens without holding everything in memory. Two places this shows up all the time in AI work:

from collections.abc import AsyncIterator, Iterable, Iterator
from itertools import batched          # Python 3.12+

def read_reviews(path: str) -> Iterator[str]:
    with open(path, encoding="utf-8") as f:
        for line in f:                  # one line in memory at a time
            if line.strip():
                yield line.strip()

def to_batches(items: Iterable[str], size: int = 32) -> Iterator[tuple[str, ...]]:
    yield from batched(items, size)     # e.g. 32 texts per embeddings request

async def stream_answer(client, model: str, prompt: str) -> AsyncIterator[str]:
    stream = await client.chat.completions.create(
        model=model, messages=[{"role": "user", "content": prompt}], stream=True)
    async for chunk in stream:          # an async generator: tokens as they arrive
        if chunk.choices and chunk.choices[0].delta.content:
            yield chunk.choices[0].delta.content

Streaming doesn't make the full answer faster. It cuts time to first token, which is what users notice. FastAPI can forward an async generator straight to the browser with StreamingResponse.

6. Context managers: never leak a connection

with guarantees cleanup: files, DB connections, HTTP clients, timers, and tracing spans. Writing your own takes about five lines:

import time
from contextlib import contextmanager
from collections.abc import Iterator

@contextmanager
def timed(label: str) -> Iterator[None]:
    start = time.perf_counter()
    try:
        yield
    finally:                              # runs even if the body raises
        print(f"{label}: {time.perf_counter() - start:.3f}s")

with timed("classify batch"):
    sum(range(1_000_000))

Async clients use async with, as in async with httpx.AsyncClient() as http: ..., so their connection pools close cleanly. It's Java's try-with-resources.

7. Packaging with uv

uv (from Astral) has become a popular all-in-one replacement for pip, venv and pip-tools. It's fast, and it writes a lockfile (uv.lock) so everyone gets the same versions. Poetry and plain pip + venv are still common, and the concepts carry over.

uv init --package review-tagger      # pyproject.toml + src/review_tagger/
cd review-tagger
uv add pydantic openai tenacity      # runtime deps -> pyproject + uv.lock
uv add --dev pytest pytest-asyncio ruff mypy
uv run pytest                        # runs inside the project venv, no "activate" needed
uv run ruff check . && uv run mypy src

pyproject.toml is your pom.xml, and uv.lock is what makes "works on my machine" true on everyone's machine.

8. pytest: test the code around the model

You can't unit-test what the model "thinks". You can test everything around it: parsing, validation, retry policy, tool dispatch, prompt assembly. The trick is a fake LLM that satisfies the same Protocol.

# tests/test_tagger.py   (pip/uv add pytest pytest-asyncio)
import pytest
from pydantic import BaseModel, ValidationError

class Label(BaseModel):
    sentiment: str
    confidence: float

class FakeLLM:                                    # satisfies the LLM Protocol, no network
    def __init__(self, replies: list[str]) -> None:
        self.replies, self.calls = replies, 0
    async def complete(self, messages) -> str:
        self.calls += 1
        return self.replies.pop(0)

async def tag(llm, text: str, max_repairs: int = 1) -> Label:
    messages = [{"role": "user", "content": text}]
    for _ in range(max_repairs + 1):
        raw = await llm.complete(messages)
        try:
            return Label.model_validate_json(raw)
        except ValidationError as e:
            messages.append({"role": "user", "content": f"Invalid JSON: {e}. Return only valid JSON."})
    raise ValueError("model never produced valid output")

@pytest.mark.asyncio
async def test_repairs_once_then_succeeds():
    llm = FakeLLM(["not json", '{"sentiment": "negative", "confidence": 0.9}'])
    assert (await tag(llm, "cold pizza")).sentiment == "negative"
    assert llm.calls == 2

@pytest.mark.parametrize("raw", ['{"sentiment": "x"}', "[]", ""])
def test_rejects_bad_payloads(raw: str):
    with pytest.raises(ValidationError):
        Label.model_validate_json(raw)

Useful extras: fixtures for shared setup (tmp_path, a seeded DuckDB), monkeypatch to swap env vars and clients, and -k / markers to keep slow "real API" tests out of the default run. Behavioural checks against a real model are evals, which get their own note.

Common interview questions

  • When would you use asyncio vs threads vs multiprocessing? asyncio for lots of I/O-bound calls (LLM/HTTP). Threads for blocking libraries that do I/O. Processes for CPU-bound work, because the GIL serialises Python bytecode (free-threaded 3.13+ builds are still experimental).
  • How do you get reliable JSON out of an LLM? Use structured outputs or JSON mode where the provider has it, validate with pydantic, repair with the error message a bounded number of times, then fail loudly and log the case.
  • What do you retry, and how? Only transient errors (429, 5xx, timeouts), with exponential backoff and jitter and a capped number of attempts. Make operations idempotent so a retry can't double-charge or double-write.
  • dataclass or pydantic? Pydantic at trust boundaries, dataclasses for internal value objects.
  • How do you test code that calls an LLM? Put the client behind an interface, use a fake for unit tests, and run evals against the real model separately.
