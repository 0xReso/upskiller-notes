Names, not boxes: Python's object model, seen from Java

pythonjavainternals

Here is a function that looks harmless.

def remember(message, history=[]):
    history.append(message)
    return history

Call it twice:

print(remember("hi"))
print(remember("how are you?"))

['hi']
['hi', 'how are you?']

The second call remembers the first. Nobody passed history, and yet it carried state across calls.

If you come from Java, your instinct says this is impossible: a default value is just a value. Wrong.

That bug, put inside an agent class, is how two users end up sharing one chat history. It happens because Python's model of what a variable is differs from Java's in one small, important way. Once you see that, a whole family of surprises stops being surprising.

By the end of this article you'll be able to predict what that function does without running it. You'll also understand why for, len and with work on objects that implement no interface at all.

This is for Java engineers writing serious Python for the first time. I assume you know what a reference and a heap are. I won't assume anything about Python internals.

Chapter 1: Variables are names (the sticky-note model)

In Java there are two kinds of variable.

A primitive like int x = 5 is a box: four bytes of storage, and the value lives inside. An object variable like List<String> xs is also a box, but what it holds is a reference, a pointer to an object on the heap.

Python has only one kind.

Every value is an object on the heap: 5, "hi", None, functions, classes, all of them. A variable is a name: a sticky note attached to one of those objects.

What does x = 5 mean, then? It doesn't mean "put 5 into x". It means: find or create the object 5, then attach the label x to it.

And where do the labels live? In a plain dictionary. Module-level names live in a dict you can actually look at:

x = 5
print(globals()["x"])      # the module namespace is a dict
globals()["y"] = 10        # so writing to it creates a variable
print(y)

5
10

(Python's tools will complain that y is undefined. It runs fine anyway.)

Every object has an identity, a type and a value. id(obj) gives the identity, which in CPython is its memory address. a is b asks "are these two labels on the same object?", like == on references in Java. a == b asks "are their values equal?", which calls the object's __eq__, like .equals().

Now the key consequence:

Assignment never copies. It only attaches another label.

a = [1, 2, 3]
b = a              # no copy: a second label on the same list
b.append(4)
print(a, a is b)

[1, 2, 3, 4] True

So far, this is exactly how Java object references behave. The difference is that Python has no primitives to break the pattern. 5 is an object and True is an object, so the same rule covers every value.

So why doesn't x = 5; y = x; y += 1 change x? That brings us to the real story: mutability.

Chapter 2: Mutability lives on the object, not the variable

Some objects can change after creation and some can't.

  • Immutable: int, float, str, bytes, tuple, frozenset, None.
  • Mutable: list, dict, set, and by default any instance of your own classes.

An immutable object offers no operation that changes it. What looks like modifying it actually builds a new object and moves the label.

x = 1000
y = x
print(x is y)     # True: two labels, one object
y += 1            # int can't change, so: make 1001, move label y
print(x, y, x is y)

True
1000 1001 False

Now do the "same" thing to a list:

xs = [1]
ys = xs
ys += [2]         # list is mutable, so += extends it IN PLACE
print(xs, xs is ys)

[1, 2] True

Same operator, opposite outcome. Why, you ask?

a += b is a request to the object. Python first tries a.__iadd__(b) (the "in-place add" hook). list implements __iadd__ by mutating itself and returning itself. int has no __iadd__, so Python falls back to a = a.__add__(b), which builds a new object and rebinds the name.

Whether += mutates or rebinds is decided by the object's type, not by the syntax.

Java's final doesn't map onto this. final List<X> xs freezes the variable (the box), while the list stays mutable. Python has no frozen variables at all; immutability is a property of objects. A tuple is immutable, but a tuple that holds a list holds a list you can still change.

Chapter 3: Calling a function attaches a new label

Python passes arguments the way Java passes object references. The parameter becomes a new name, attached to the same object the caller passed. The official term is call by sharing.

Two things can happen inside the function, and they have different effects:

def mutate(items):
    items.append("added")      # changes the shared object

def rebind(items):
    items = ["brand new"]      # moves the local label only

data = ["original"]
mutate(data)
rebind(data)
print(data)

['original', 'added']

Mutation is visible to the caller because there is only one list. Rebinding is invisible because it moves a label that only exists inside the function.

If you know Java, you know this already. The only twist is that ints and strings follow the same rule. You'll never notice, though, because they're immutable: there is nothing to mutate, so all you can do is rebind.

Chapter 4: Defaults are evaluated once (the bug from the intro)

Back to remember.

A def statement is executed, like any other statement. When Python runs it, it builds a function object, and at that moment it evaluates the default expressions once and stores the resulting objects on the function:

def remember(message, history=[]):
    history.append(message)
    return history

print(remember.__defaults__)   # the list already exists
remember("hi")
print(remember.__defaults__)   # ...and now it has been mutated

([],)
(['hi'],)

Every call that omits history receives a label on that one list, the one stored in __defaults__. It's a mutable object shared by every call, which makes it a bit like a static field you never declared.

The fix is to make the default an immutable sentinel and create the list inside the call:

def remember(message, history=None):
    if history is None:        # 'is None': identity check, the idiom
        history = []           # a fresh list per call
    history.append(message)
    return history

The same trap exists one level up, on classes. Names assigned in a class body become attributes of the class object, shared by all instances. Java would call them static fields:

class Agent:
    history = []               # class attribute: ONE list for all

    def ask(self, q):
        self.history.append(q)

a, b = Agent(), Agent()
a.ask("refund status?")
print(b.history)               # user b sees user a's question

['refund status?']

self.history looked the name up on the instance, didn't find it, and fell back to the class. Per-instance state belongs in __init__ (self.history = []).

The libraries know this trap well. dataclasses refuses a list default outright and asks for field(default_factory=list), a function it calls once per instance. pydantic quietly copies a mutable default for each instance. That's a good reason to use them for anything that holds state.

Chapter 5: Protocols, not interfaces

In Java, the for loop works on anything that implements Iterable<T>. The compiler checks the declaration.

Python has no implements. Instead, the language defines protocols: sets of specially named methods. They start and end with double underscores, so they're nicknamed dunder methods. Syntax and built-ins call these methods for you:

You write Python calls Java's nearest equivalent
len(x) x.__len__() Collection.size()
x[i] x.__getitem__(i) List.get(i)
for v in x iter(x) → x.__iter__(), then __next__() until StopIteration Iterable / Iterator
a == b a.__eq__(b) equals
hash(x) x.__hash__() hashCode
with x as y: y = x.__enter__() … x.__exit__(...) try-with-resources / AutoCloseable
print(x) x.__str__() (else __repr__) toString

If an object has the methods, it works. That's all. This is duck typing: if it walks like an iterator, it is one.

Here's a conversation transcript that slots into the language with no base class at all:

class Transcript:
    def __init__(self):
        self._turns = []

    def add(self, role, text):
        self._turns.append((role, text))

    def __len__(self):
        return len(self._turns)

    def __getitem__(self, i):          # enables t[0], t[-2:]
        return self._turns[i]

    def __iter__(self):                # enables for-loops
        return iter(self._turns)

    def __repr__(self):
        return f"Transcript({len(self)} turns)"

t = Transcript()
t.add("user", "Where is my refund?")
t.add("assistant", "Checking now.")
print(t, len(t), t[-1])
for role, text in t:
    print(f"{role:>9}: {text}")

Transcript(2 turns) 2 ('assistant', 'Checking now.')
     user: Where is my refund?
assistant: Checking now.

with works the same way. __enter__ runs on the way in, and __exit__ runs on the way out even if an exception was raised. It receives the exception, and if it returns True the exception is swallowed. This is exactly try-with-resources, without the interface:

import time

class Timer:
    def __enter__(self):
        self.t0 = time.perf_counter()
        return self                    # bound to the name after 'as'

    def __exit__(self, exc_type, exc, tb):
        self.ms = (time.perf_counter() - self.t0) * 1000
        print(f"took {self.ms:.1f} ms, error={exc_type}")
        return False                   # don't swallow exceptions

with Timer():
    sum(range(1_000_000))

You still lose something compared to Java: nobody checks the contract before you run. To get that back, Python offers typing.Protocol, which gives you structural interfaces. You describe the methods, and static checkers (tools like mypy or pyright that read type hints without running code) accept any class whose shape matches. At runtime, Python ignores all of it. (That last fact is important enough to get its own article, on type hints and pydantic.)

Chapter 6: Generators, functions that pause

One protocol needs extra attention, because LLM code uses it everywhere: the iterator protocol, implemented with yield.

A function containing yield is a generator function. Calling it doesn't run the body. It returns a generator object, a paused stack frame. Each next() resumes the frame until the next yield, hands out that value, and freezes again with all local variables intact:

def countdown(n):
    print("starting")
    while n > 0:
        yield n          # pause here, hand n to the caller
        n -= 1
    print("done")        # then StopIteration ends the loop

g = countdown(2)         # nothing printed yet: body hasn't run
print(next(g))
print(next(g))
for _ in g:              # resumes; runs to the end
    pass

starting
2
1
done

Java's closest relative is an Iterator you write by hand, keeping state in fields. Here, the program counter itself is the state.

Why does this matter for AI work? Because laziness lets you process data that doesn't fit in memory, and streams that haven't arrived yet:

import json, io

def read_jsonl(f):
    for line in f:              # file objects are lazy iterators too
        if line.strip():
            yield json.loads(line)

def only_failed(rows):
    for r in rows:
        if r["status"] == "failed":
            yield r

f = io.StringIO('{"id":1,"status":"ok"}\n'
                '{"id":2,"status":"failed"}\n')
for row in only_failed(read_jsonl(f)):   # one row in memory at a time
    print(row)

{'id': 2, 'status': 'failed'}

Hold on to this picture: a function whose frame can be suspended and resumed. It's the entire foundation of asyncio, which is a story for another article.

Chapter 7: Ah moments

A few surprises that follow directly from everything above.

The tuple that both fails and succeeds

t = ([1],)
try:
    t[0] += [2]
except TypeError as e:
    print("error:", e)
print(t)

error: 'tuple' object does not support item assignment
([1, 2],)

It raised an error and the change happened. t[0] += [2] runs as two steps: t[0].__iadd__([2]), which mutates the list in place and succeeds, and then t[0] = result, which tries to assign into the tuple and fails. Chapter 2 in miniature.

Closures capture names, not values

fns = [lambda: i for i in range(3)]
print([f() for f in fns])

[2, 2, 2]

Each lambda holds the name i, not a snapshot of its value. They look the name up when called, and by then the loop has finished at 2. Java forces captured variables to be "effectively final" precisely to stop this. The fix is to bind the value at definition time, using a default argument (evaluated once, as in Chapter 4): lambda i=i: i.

is is not ==

x is 1000 might be True or False depending on how the objects were created. CPython caches the small integers -5 to 256 and reuses some strings, so identity checks sometimes look like they work. Use is only for singletons like None, True and False. Use == for values.

Copies are shallow unless you ask

list(xs), xs[:], dict(d) and copy.copy create a new outer container, but the elements are the same objects. A list of dicts, copied that way, still shares every dict. copy.deepcopy walks the whole graph. When you take a "snapshot" of agent state, decide which one you mean.

Epilogue

Everything in this article follows from three facts:

Every value is an object. A variable is a name attached to an object. Whether something changes in place is up to the object.

With those, the mutable default, the shared class attribute, += behaving two ways and the half-failed tuple assignment are no longer folklore to memorise. They're consequences you can predict.

And protocols explain why Python code looks so light next to Java: the language trusts shape over declarations. You'll lean on that constantly, since pydantic models, async iterators and streaming responses are all just objects with the right dunder methods.
